# ADR 0002: 音声・認証・決済・共有の実装計画

Status: Approved for demo implementation — final developer review pending

全フェーズ実施を依頼された。既存Phase 1のReactとUI非依存coreを再利用し、Supabase Edge Functions、Auth、PostgreSQL/RLSを追加する。音声の認証要件のため、Phase 3の最小認証基盤をPhase 2より先に実装する案。

## BYOK比較

| 方式 | 利点 | 問題 |
|---|---|---|
| サーバーで利用者別に暗号化保管 | 支援者が初期設定後、利用者がキー操作不要 | 復号権限・鍵ローテーション・削除・侵害時対応が必要 |
| 毎回サーバーへ入力、永続保管なし | 保存時の秘密情報を減らせる | 高齢者の操作負担が大きく、サーバーへの一時送信は残る |
| ブラウザから標準キーで直接通信 | サーバーがキーを預からない | 標準キーのクライアント露出、端末管理、利用権限の制御が問題 |

提案: サーバー側AES-GCM暗号化、別管理のマスター鍵、ユーザー別キー。フロントへは短命認証のみ。キーをログ・localStorageに入れない。採用記録に従って実装する。

## 音声

公式Realtime GAのWebRTCフロー。バックエンドで認証・Premium権限・利用制限を検証し、短命接続情報を発行。ブラウザ側の終了だけで費用上限を保証できないため、プロバイダー側利用上限およびサーバー側の監視・制御方式を確定する必要がある。

## Stripe

テストモードから開始。署名検証済みWebhookでサーバー会員状態を更新。イベント重複・順序逆転・解約・支払い失敗をテスト。価格と有料機能は正式公開前に確定。既存Stripe契約や本番課金操作は承認なしに実施しない。

## Phase 7

共有前に項目単位で本人の明示承認、支援者は招待・許可された範囲のみ。全文・音声は保存しない。撤回・訂正・削除を提供する。AI推測は候補として提示し、承認まで記録・送信しない。同意能力・代理権限が不明な場合は共有を停止する。

## 採用記録（2026-10-10）

Status: Approved for demo implementation。ユーザーの「今回のみ全体を遂行させてデモ提示まで」指示により実装を進めた。上記提案の音声方式は次の確定案に更新する。

BYOKは利用者別AES-GCM暗号化とサーバー保管を採用。WebRTCは統合方式でSDPを認証済みバックエンドからOpenAIへ送信し、クライアントへSDP回答だけを返す。標準キー・短命キーをクライアントへ渡さない。60秒のサーバー終了監視と日次予約枠を設けるが、障害時の料金上限保証は実接続の運用確認が必要。既定でRealtime無効。Stripeはテストモードのみ。

模擬デモを独立したビルド・ループバックサーバーに分離し、実APIにデモの役割切替や課金模擬を持ち込まない。Phase 7は限定された候補抽出と本人の項目別同意を採用し、通常会話の永続保存・企業転用は実装しない。

最終セキュリティ・プライバシー・決済レビュー、本番承認は未完了。
